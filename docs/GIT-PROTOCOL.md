# Git Smart HTTP and Protocol Reference

This document provides an exhaustive technical specification of how **ghforge** (`github-core-clone-01`) serves Git over Smart HTTP (`githttp.ts`) and handles underlying Git object and pack plumbing (`gitcore.ts`). Every claim herein is strictly grounded in the codebase implementation.

---

## 1. Request Routing and Service Endpoints

Every Git Smart HTTP request targeting a repository is routed through `handleGitRequest(lookup, request)` in `githttp.ts`.

### 1.1 URL Matching Pattern
Incoming request paths are matched against the following regular expression:
```typescript
const match = /^\/([A-Za-z0-9][A-Za-z0-9._-]{0,99})\/([A-Za-z0-9][A-Za-z0-9._-]{0,99})\.git(\/.*)?$/.exec(request.path);
```
- **Owner (`match[1]`)**: A valid login name (up to 100 characters matching `[A-Za-z0-9._-]`).
- **Repository (`match[2]`)**: A valid repository name ending in `.git`.
- **Tail (`match[3]`)**: The sub-path within the repository git service (e.g., `/info/refs`, `/git-upload-pack`, `/git-receive-pack`).

If the path does not match, `handleGitRequest` returns `null` (resulting in a 404 Not Found at the application level). If the repository `lookup(owner, name)` returns `null`, a 404 response is returned with body `'not found\n'`.

## 2. The `info/refs` Advertisement

Clients initiate interactions by fetching `/{owner}/{repo}.git/info/refs?service=<service>`, where `<service>` is either `git-upload-pack` or `git-receive-pack`.

### 2.1 Service Validation
If the `service` query parameter is missing or set to anything other than `git-upload-pack` or `git-receive-pack`, ghforge returns:
- **Status**: `400 Bad Request`
- **Content-Type**: `text/plain`
- **Body**: `'bad service\n'`

### 2.2 Protocol Version 2 Detection
If the request includes a `Git-Protocol` header containing `version=2` (checked via `(request.protocolHeader ?? '').includes('version=2')`), and the service is `git-upload-pack`, ghforge serves the protocol v2 advertisement. Otherwise, it serves the protocol v0 advertisement.

### 2.3 Protocol v2 Advertisement
Generated by `v2Advertisement('git-upload-pack')`:
1. `# service=git-upload-pack\n` (pkt-line)
2. `0000` (FLUSH_PKT)
3. `version 2\n` (data pkt-line)
4. `agent=ghforge/1.0\n` (data pkt-line)
5. `ls-refs=unborn\n` (data pkt-line)
6. `fetch=shallow filter ofs-delta\n` (data pkt-line)
7. `object-format=sha1\n` (data pkt-line)
8. `0000` (FLUSH_PKT)

### 2.4 Protocol v0 Advertisement (`git-receive-pack`)
Generated by `v0Advertisement(repo, 'git-receive-pack')`:
- Starts with `# service=git-receive-pack\n` followed by a flush packet (`0000`).
- Capabilities advertised:
  ```text
  report-status report-status-v2 delete-refs side-band-64k ofs-delta agent=ghforge/1.0 object-format=sha1
  ```
- If the repository is null or has zero refs (`repo.refs.size === 0`), it emits a zero-oid capability line:
  ```text
  0000000000000000000000000000000000000000 capabilities^{}\0report-status report-status-v2 delete-refs side-band-64k ofs-delta agent=ghforge/1.0 object-format=sha1\n
  ```
- Otherwise, it iterates over `orderedRefs(repo)` (sorting refs alphabetically, with `HEAD` first if present). The first ref line attaches capabilities separated by a null byte (`\0`), and subsequent ref lines are standard `<oid> <ref>\n` pkt-lines.
- Terminates with a flush packet (`0000`).

### 2.5 Protocol v0 Advertisement (`git-upload-pack`)
Generated by `v0Advertisement(repo, 'git-upload-pack')`:
- Starts with `# service=git-upload-pack\n` followed by a flush packet (`0000`).
- Capabilities advertised:
  ```text
  multi_ack_detailed multi_ack side-band-64k side-band thin-pack ofs-delta shallow deepen-since deepen-not no-progress include-tag symref=HEAD:refs/heads/<defaultBranch> agent=ghforge/1.0 object-format=sha1
  ```
- If refs are empty, emits `0000000000000000000000000000000000000000 capabilities^{}\0<capabilities>\n` followed by a flush packet.
- If refs exist, emits `HEAD` pointing to `refs/heads/<defaultBranch>` (or `ZERO_OID` if unset) with capabilities after `\0`, followed by all other ordered refs, and terminates with a flush packet (`0000`).

## 3. Git Protocol v2 Handlers (`ls-refs` and `fetch`)

When `wantsV2` is active, requests to `/git-upload-pack` are parsed via `parseV2Request(request.body)`.

### 3.1 Parsing v2 Requests
`parseV2Request` parses pkt-lines from the request body:
- Lines before the delimiter (`0001`, `DELIM_PKT`) containing `command=` specify the command (e.g., `command=ls-refs` or `command=fetch`).
- Lines after the delimiter are arguments. Ignored lines include empty lines, `object-format=`, `agent=`, and `session-id=`.
- Arguments without spaces are stored as `true` (e.g., `symrefs`, `peel`, `unborn`). Arguments with spaces are stored as `key -> value`.

### 3.2 `ls-refs` Command Handling
Implemented in `lsRefsResponse(repo, args)`:
- Supports arguments: `symrefs`, `peel`, `unborn`, and `ref-prefix`.
- Collects ref prefixes.
- Evaluates `HEAD`:
  - If `HEAD` is unborn (default branch target OID not in `repo.refs`) and `unborn` arg is present and prefixes match `HEAD`, emits `unborn HEAD symref-target:refs/heads/<branch>` (or `unborn HEAD`).
  - If `HEAD` has a valid OID and matches `HEAD`, emits `<oid> HEAD [symref-target:...]`.
- Iterates through `orderedRefs(repo)`:
  - Skips `HEAD`.
  - Filters by `ref-prefix` matches.
  - If `peel` is requested, computes peeled OID (`peel(repo, oid)`). If peeled differs from OID, appends ` peeled:<peeled>`.
  - Emits each matching ref as a pkt-line.
- Terminates with a flush packet (`0000`).

### 3.3 `fetch` Command Handling (`fetchV2Response`)
- Parses client haves from pkt-lines (`have <oid>`).
- Parses fetch arguments (`want`, `shallow`, `deepen`) via `parseFetchArgs`.
- Calls `selectFetchObjects(repo, spec)` to determine the required object closure.
- Response sections:
  1. **Acknowledgments**: If client sent haves and objects were found, emits `acknowledgments\n` followed by `NAK\n` and a flush packet (`0000`).
  2. **Shallow-Info**: If there are new shallow boundaries or unshallow commits, emits `shallow-info\n`, followed by `shallow <oid>\n` or `unshallow <oid>\n` lines, terminated by a flush packet (`0000`).
  3. **Packfile**: Emits `packfile\n`, followed by the pack data encoded with sideband channel 1 (`sideband(1, pack)`), terminated by a flush packet (`0000`).

## 4. Object Selection and Closure (`selectFetchObjects`)

The function `selectFetchObjects` computes the exact set of git objects (commits, trees, blobs, tags) to send to a fetching client:
1. **Want filtering**: Filters requested OIDs (`spec.wants`) to those present in `repo.objects`.
2. **Have closure (`haveClosure`)**: If the client provides `haves` (and optional client `shallow` boundaries), ghforge computes all ancestors held by the client, stopping at client shallow boundaries.
3. **Commit walking**: For each want (handling annotated tags by peeling/walking to their target commit), commits are walked newest-first up to `spec.depth` generations using `walkCommits`.
4. **Tree and Blob inclusion**: For each included commit, its commit object, tree, and recursively all child trees and blobs are included via `sendObject` and `sendTree`, unless already present in `haveClosure`.
5. **Shallow boundaries**: Detects new shallow boundaries (commits whose parents are neither included nor in `haveClosure`) and unshallow changes, returning them in `shallow` and `unshallow` arrays.

## 5. Receive-Pack (Protocol v0 Push)

Managed by `handleReceivePack(repo, request)` in `githttp.ts` and `applyReceivePack(repo, commands, pack)` in `store.ts`.

### 5.1 Request Parsing
- Parses request body pkt-lines.
- The first packet contains the first command and optional capabilities after a null byte (`\0`).
- Subsequent command lines are read until a flush packet (`0000`) is encountered.
- Each command consists of: `oldOid`, `newOid`, and `ref`.
- Any remaining bytes after the flush packet (if `consumed < request.body.length` and length >= 12) are treated as the uploaded packfile (`pack`).

### 5.2 Unpack and Object Verification
- If `pack` is provided, `readPack(pack)` unpacks the packfile.
- For every unpacked object, `hashObject(object.type, object.data) === oid` is verified. If invalid, `unpackOk` is set to `false`.
- Valid objects are stored in `repo.objects`.

### 5.3 Push Command Execution & Non-Fast-Forward Refusals
If `unpackOk` is true, each push command is validated and executed:
1. **Deletion (`newOid === ZERO_OID`)**:
   - If ref does not exist: report `ok: false, reason: 'no such ref'`.
   - If `oldOid !== current` (stale info): report `ok: false, reason: 'stale info'`.
   - Otherwise, deletes ref and reports `ok: true`.
2. **Missing Objects**:
   - If `!repo.objects.has(command.newOid)`: report `ok: false, reason: 'missing objects'`.
3. **Creation (`oldOid === ZERO_OID`)**:
   - If ref already exists: report `ok: false, reason: 'ref already exists'`.
   - Otherwise, sets ref to `newOid` and reports `ok: true`.
4. **Updates & Non-Fast-Forward Refusal Rule**:
   - If `command.oldOid !== current`: report `ok: false, reason: 'stale info'`.
   - If `!isAncestor(repo, command.oldOid, command.newOid)`:
     - **Non-Fast-Forward Refusal Rule**: Refuses the push and reports `ok: false, reason: 'non-fast-forward'`, which formats as:
       `ng <ref> non-fast-forward`
   - Otherwise, updates ref and reports `ok: true`.

### 5.4 Report Status and Sideband-64k
- Constructs report lines: `unpack ok\n` (or `unpack <detail>\n`), followed by `ok <ref>\n` or `ng <ref> <reason>\n`, terminated by a flush packet (`0000`).
- If client requested `side-band-64k` in capabilities, the report body is wrapped in sideband channel 1 (`sideband(1, reportBody)`) followed by a flush packet.

## 6. Git Packfile Plumbing and Store Object Model (`gitcore.ts`)

ghforge implements pure-buffer Git object encoding, decoding, pack writing, and pack reading.

### 6.1 Pkt-Line Framing
- `pktLine(payload)`: Prepends a 4-character hex length (including the 4 length bytes itself) to the UTF-8 or Buffer payload.
- `FLUSH_PKT`: `0000` (Buffer).
- `DELIM_PKT`: `0001` (Buffer).
- `parsePktLines(buf)`: Iterates through byte buffer, parsing 4-hex-digit length prefixes. Handles flush (`0000`), delim (`0001`), and data packets.

### 6.2 Object Types and Hashing
- Supported object types (`ObjType`): `'blob'`, `'tree'`, `'commit'`, `'tag'`.
- `hashObject(type, data)`: Computes SHA-1 hash of `${type} ${data.length}\0` concatenated with `data`.

### 6.3 Trees, Commits, and Tags
- **Trees**: `parseTree(data)` decodes binary tree entries (mode, name, 20-byte binary OID). `buildTree(entries)` sorts entries (`treeSort`: directory entries ordered with trailing `/`) and encodes them into binary buffers.
- **Commits**: `parseCommit(data)` parses header fields (`tree`, `parent`, `author`, `committer`) and message body. `buildCommit` encodes commit objects.
- **Tags**: `parseTag` and `buildTag` handle annotated tag objects (`object`, `type`, `tag`, `tagger`, `message`).

### 6.4 Packfile Writing (`writePack`)
- Writes magic `PACK`, version 2 (uint32be), and object count (uint32be).
- For each object:
  - Encodes variable-length object header (`objHeader`) containing object type number (`commit: 1, tree: 2, blob: 3, tag: 4`) and size varint.
  - Deflates object data using `zlib.deflateSync(data, { level: 1 })`.
- Appends SHA-1 checksum trailer computed over all preceding pack bytes.

### 6.5 Packfile Reading (`readPack`)
- Verifies `PACK` magic and version 2.
- Parses declared object count.
- Iterates through entries:
  - Decodes variable-length object header and size.
  - Handles object types 1-4 (standard types) and delta types (`ofs_delta` type 6, `ref_delta` type 7).
  - For `ofs_delta`, decodes negative offset and zlib stream.
  - For `ref_delta`, reads 20-byte base OID and zlib stream.
  - Uses binary-search inflation (`inflateWithSize`) to robustly handle zlib streams embedded in packfiles.
- Resolves delta chains recursively (`resolveOffset` / `resolveByOid`), applying binary deltas via `applyDelta`.
- Computes SHA-1 hash for each resolved object and populates the returned map.
- `verifyPackChecksum(pack)` verifies the trailing 20-byte SHA-1 checksum against `sha1Hex(pack without trailer)`.
